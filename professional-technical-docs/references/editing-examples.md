# 语义保真示例

以下是说明改写边界的合成例句，不代表某产品的实际行为或实验记录。

## 保留条件与并行关系

原句：只有两个计算节点的驱动版本一致，且两个工作进程都完成加载后，客户端才可以同时向两个节点发送请求。

可改：确认两个计算节点的驱动版本一致，并等待两个工作进程加载完成。满足这两个条件后，客户端可同时向两个节点发送请求。

检查：两个条件均保留；并行请求没有改成先后请求；没有编造超时时限。

## 区分现象和根因

原句：页面连接失败可能由代理配置引起，本机健康接口返回成功尚不能排除外部路径的问题。

可改：本机健康接口返回成功。外部页面仍连接失败，需要检查代理配置及外部访问路径，才能判断原因。

检查：没有断言代理一定错误，也没有把本机成功改成外网已通过。

## 保留状态层级

原句：服务配置已经保存，是否开机自动启动尚未验证。

可改：服务配置已保存。开机自动启动行为未验证。

不应改为“服务已配置完成，重启后会自动恢复”。保存配置不提供这项证据。

## 代码与输出不能靠润色纠错

若资料中的 HTTP 200 响应包含 `{"result":{"ok":false}}`，先依据该接口的契约判定业务失败，再写错误处理。不能把 200 直接改述为“任务成功”，也不能为统一格式把 JSON 改成非标准引号。

若某版本的命令行帮助没有相应参数，不能为了让步骤完整而补造一个看似合理的选项。应核对目标版本实现或明确该步骤待确认。

## 保留范围与数字

“仅在列出的测试组合中通过”和“在所有环境中通过”不同；“未证明问题来自组件 A”不等于“已证明组件 A 无问题”。调整句式和引用时保留原有范围、排除关系及证据强度。

## 处理空话

“本方案提供高效、稳定、无缝的体验”没有可核对信息。若来源仅说明可以通过指定入口访问服务，正文就说明访问入口和条件，不添加性能、可靠性或易用性结论。
