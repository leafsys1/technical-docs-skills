# 按文档任务组织内容

这些是内容契约，不是必须逐字采用的目录。优先使用项目模板；合并小节，删除不适用的部分，不留空标题或用套话填充篇幅。文档版本、适用对象、验证范围与来源集中说明一次，变化处再补充。

## 模型部署手册

读者任务：将指定模型和框架在声明的硬件/系统组合上部署，并获得可验证的服务。

建议内容顺序：

1. 适用范围与部署方案：读者、已验证版本组合、部署形态、关键限制；多节点或多组件用简明架构图说明角色和调用方向。
2. 环境与准备：硬件和架构、驱动/运行时、镜像或依赖锁定、权限、存储、网络、模型文件/修订与完整性。
3. 标准部署路径：依赖与模型准备、配置、启动顺序、所用参数及关键取舍；区分控制端、目标端和容器内。
4. 服务验收：对应实例就绪、最小业务请求、正确性判据、客户端访问路径；有持久性要求时说明实际验证过的恢复边界。
5. 运维和异常：状态、日志、停止与启动、常见故障的判断分支、升级/回退及数据保护。

参数表按实际需要记录名称、作用、值/默认值、单位、约束、适用版本、调整依据。主流程只放完成该方案所需内容，其他参数放参考部分。

重点审查：不同框架/架构的参数混用；镜像标签浮动；模型修订和量化信息缺失；主机路径与容器路径混淆；资源被其他任务占用；用端口监听代替模型验收。

## 测试手册或测试规程

读者任务：在给定环境下执行一组测试，用一致口径判定产品是否满足要求。

建议内容：

- 测试目标、对象和版本；覆盖范围及明确排除项。
- 环境、工具、依赖、测试数据来源与准备；执行前的基线、隔离条件和清理策略。
- 测试用例。每个用例可定位到目标/需求，包含编号、前置状态、输入和操作、预期结果、通过/失败判据、实际记录位置及必要的恢复动作。
- 执行顺序和依赖。可独立的用例不强加串行；会改变共享状态的用例明确隔离或顺序。
- 结果记录、失败处置、复测范围和最终判定方法。

**测试手册不是测试报告。** 手册可以写预期结果和判据；报告需要实际版本、执行记录、结果和缺陷。不要在未执行的用例中预填“通过”。

性能测试另需明确：基线与变量、输入/输出长度及分布、并发或到达率、预热、持续时间/样本数、计时边界、失败与截断的计入方式、重复测量和允许波动。阈值来自需求或已说明的评价目标，不能临时编造。

## 最佳实践指南

读者任务：在明确条件下选择方案或改进现有方案，理解收益、代价和不适用情况。

按具体问题组织，每项实践写清：

- 适用问题和触发条件，以及不宜采用的场景。
- 推荐做法与可核对的配置/实现；为什么适用。
- 依据和验证范围；收益与代价，必要的替代方案。
- 实施步骤、结果检查和退出/恢复条件。

行业常见做法、官方建议、代码分析和实际实验分开归因。缺少比较证据时，可给有条件的建议，不能宣称普遍最优。不要将一个设备、一个负载的性能结论推广成所有部署的统一规则。

## 运维规程与故障排查

围绕运行任务组织：触发条件、检查、操作、验证、停止/升级处理。故障部分按可观察现象分支，每个分支给出收集内容、判断条件和下一步。时间、请求标识、实例/进程、版本要能关联；敏感日志需脱敏。

操作会影响现有任务时，提前说明影响、可选窗口和恢复责任。不要把“服务已配置”“当前运行”“持久启用”“业务可用”合成一个模糊的成功状态。

## 成套手册与交付格式

- 入口文档提供读者、范围、标准起点与导航；操作页、概念页和参数参考各有主要任务并相互链接。
- 核心事实只在一个权威位置维护，其他位置引用；不要复制多份参数表造成版本漂移。
- 表格适合环境、参数、用例和比较数据；过程用编号步骤；因果和解释用段落。图像承担结构说明时有文字替代，不能只在截图里提供必要参数。
- 文件名、编号、标题层级、术语、单位、表图标题与引用按同一项目规则保持一致。不得为了统一命名破坏已有链接或项目结构。
- Word/PDF 按项目模板统一样式、字号、页眉页脚、页码、表格跨页与代码字体，并打开最终导出文件检查；Markdown 不宣称已经验证这些属性。
