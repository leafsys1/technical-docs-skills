# 操作与证据契约

适用于安装、部署、配置、测试、升级、运维和故障处理。按任务风险采用，不要求每个小步骤重复填写一张表。

## 1. 环境和适用范围

在操作之前给出决定步骤是否适用的信息：

| 内容 | 需要确认的信息 |
| --- | --- |
| 版本 | 产品、框架、插件、镜像和模型的准确版本或提交；相互兼容的组合 |
| 硬件 | CPU 架构、设备型号与数量、内存/显存、拓扑；与步骤无关的字段可省略 |
| 系统 | OS、内核、驱动及运行时；按目标硬件确认 CUDA、CANN 等依赖，不互相代用 |
| 位置 | 本机/目标主机/容器、执行用户、工作目录、配置和产物位置 |
| 起始状态 | 全新安装或已有服务、是否有运行任务、需要保留的数据及已具备权限 |
| 输入 | 模型标识与修订、权重/数据来源、格式、量化与必要校验，不把文件存在当完整性证明 |
| 接口 | 端口、路径、协议、认证方式、客户端访问位置及必要网络条件 |

软件要求和当前实测环境分开写。不能由“在一个版本上通过”推导“所有更高版本兼容”。从目标版本源码、帮助或官方资料核对参数；不把相似框架或其他架构的参数直接移植。

## 2. 事实与结果的依据

关键事实保留依据位置及适用版本。可以是一条文件与行号、提交链接、帮助输出或实际执行记录，不强制给每句正文加标签。

- 已实测：能定位执行时间、环境/版本、命令、输入与实际结果；结果只覆盖该范围。
- 已核对：静态依据支持接口、默认值或配置含义；不能替代现场运行。
- 预期/示例：告诉读者如何判断，不假装是已发生的输出。
- 未确认：指出具体缺口和验证方式。无关缺口不阻塞整份草案；影响安全、核心步骤或验收时不能标为正式可复现版本。

比较或性能结论还需保存控制变量、负载、指标定义、样本/轮次、基线与限制。区分吞吐与单请求时延、首 token 与后续 token 时延、平均值与分位数、整体流程与某个算子的耗时。不能把预热、失败请求、截断输出或不同完成条件混成可比较数据。

## 3. 步骤需要回答的问题

章节统一说明执行上下文，步骤继承该上下文；上下文改变时显式切换。一个步骤围绕一个可检查的主要动作，不拆散必须同时成立的条件。

1. **何时执行**：起始状态、前置结果与分支选择条件。
2. **在哪里执行**：主机、容器、用户、Shell、目录；控制端命令不与目标端命令混排。
3. **执行什么**：命令/配置/界面动作、输入变量及影响对象。
4. **观察什么**：预期文件、状态或响应；实际输出与示例明确区分。
5. **怎样判定**：通过条件、允许变化的字段、等待时限及其依据。
6. **失败怎么办**：停止条件、保留的证据、下一项检查或恢复位置。

简单查询可用一句说明加命令。涉及数据、服务或权限的改变，要在动作之前说明影响和恢复要求；不要在所有无害命令前堆叠警告。

## 4. 可复制的命令与配置

- 命令、输出、配置分别使用对应语言的代码块。可执行命令不带终端提示符、行号或省略号；使用说明的语法摘要另标为语法示意。
- 变量先定义来源和有效值，再在命令中引用；说明是否需要 `export`、新终端是否保留、服务进程如何获得它们。不能依赖作者当前 Shell 的隐含状态。
- 不把 `<HOST>`、`<PATH>` 直接放进可复制的 Shell 命令；尖括号可能被解释为重定向。使用已说明的引号与变量，必要时采用 `${VAR:?缺少必要变量}` 提前失败。
- 路径按读者环境绑定。不要混用作者本机路径、容器内路径和远端挂载点；相对路径有已声明的基准目录，日志/下载/测试产物有明确任务目录。
- 参数、默认值、配置语法和拼写与目标版本一致。JSON 代码块不插入注释，续行符后不附注释或空白，不把长命令折成不可执行的段落。
- 区分可重复执行与只执行一次的步骤；已有文件/服务/数据存在时写清覆盖策略和重复执行的后果。
- 密钥由环境变量、受保护文件或凭据管理机制提供；正文、截图、日志和示例均不含真实密钥。不要为展示值而输出整个环境或配置文件。
- 文字润色不能修改标识符、大小写、引号、重定向符、通配符、运算符或真实错误原文。修改命令本身需要重新核对技术依据。

以下仅演示操作说明方式，不是现场状态记录。假设本节已要求读者将 `MODEL_SERVICE` 设置为实际的用户服务名称，在服务所属用户的目标 Linux 终端查询：

```bash
: "${MODEL_SERVICE:?请先指定本节的用户服务名称}"
systemctl --user show "$MODEL_SERVICE" -p ActiveState -p SubState
```

预期状态示例为 `ActiveState=active`、`SubState=running`。这只说明进程状态，不能单独证明模型可用。系统级服务应使用对应的系统服务命令；不能只删掉 `--user` 后仍声称操作同一个服务。

## 5. 分层验收

按读者任务选择真正需要的层级，不把某一层通过外推到其他层：

| 检查 | 能证明的事实 | 还不能证明的事实 |
| --- | --- | --- |
| 文件/版本核对 | 指定文件存在、修订匹配 | 权重完整、版本组合可运行 |
| 进程与监听 | 进程存活、端口可连接 | 模型加载完成、业务请求正确 |
| 就绪和接口 | 目标实例就绪、响应符合接口约定 | 完整用户流程、外部访问、长期稳定性 |
| 功能用例 | 给定输入下的实际流程和断言通过 | 未覆盖输入、性能、其他硬件组合 |
| 持久化恢复 | 实际验证过的服务/主机重启边界下恢复 | 未执行过的整机重启或故障恢复 |
| 性能测试 | 给定版本、负载及测量口径下的指标 | 其他负载或架构上的相同收益 |

验证应绑定当前实例和版本，不能读取旧进程的成功日志作为新实例就绪依据。退出码、HTTP 状态和业务结果分别检查；某些 RPC 会在 HTTP 200 中返回业务错误，按该接口契约判断。

外网使用的产品需要从外部访问路径验证认证、资源、实时连接及目标用户流程。本机地址、测试域名映射或绕过反代的请求只证明其实际经过的路径。

需要开机恢复时，说明启动管理器、用户级/系统级作用域、持久定义、自启动依赖、环境与数据目录，并分别验证服务重启和整机重启。临时托管、自启动配置已启用、实际重启已恢复是不同结论。

## 6. 异常与回退

先给现象与可区分的判断依据，再给处理动作，不把“可能原因”写成确定根因。低风险、有信息增益的检查优先；同一错误原地重试没有新增依据时应改变检查路径。

回退说明至少覆盖：触发条件、恢复对象、真实可用的备份/基线、执行权限、受影响任务、需要保留的新数据、恢复后的验证。源码、运行文件、配置、数据库和模型/数据分别处理；不能因应用回退而默认用旧数据库覆盖部署后的新业务数据。

无法安全自动恢复时，写明停止点、需要保留的日志/状态及联系角色。不编造恢复脚本、备份文件或超时值；数值来自产品约束、用户要求或有依据的运行策略。
